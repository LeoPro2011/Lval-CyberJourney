## Les quatre approches

- **Simple analysis :** chercher les chaînes de caractères lisibles et les informations immédiatement visibles dans un binaire.
- **Static analysis :** examiner le désassemblage ou le pseudocode décompilé sans exécuter le programme.
- **Dynamic analysis :** exécuter le programme et observer son comportement, notamment avec un débogueur.
- **Symbolic execution :** raisonner sur les conditions du programme à l'aide de variables symboliques et de contraintes, puis chercher une entrée qui satisfait le chemin de réussite.

## Analyse simple : outils et notions

- **`xxd` :** affiche les octets d'un fichier en hexadécimal, avec leurs offsets et une représentation ASCII lorsqu'elle existe. Cela permet notamment d'examiner les premiers octets et de reconnaître des signatures de fichiers (*magic bytes*). Ce n'est pas la même chose que l'extraction de texte avec `strings`.
- **`checksec` :** donne un aperçu de protections présentes dans un binaire, notamment Canary, NX, PIE et RELRO. Ces protections compliquent certaines exploitations, mais ne garantissent pas à elles seules l'absence de vulnérabilités.
- **`strings` :** extrait les séquences de caractères imprimables. C'est un premier moyen de chercher des messages, chemins, noms ou secrets potentiellement intégrés en clair. L'absence d'une chaîne dans le résultat ne prouve pas que l'information est absente : elle peut être encodée, chiffrée ou construite à l'exécution.

Les commandes ont été utilisées sur un binaire fourni pour l'exercice.

## Analyse statique : Ghidra et XOR

J'ai importé le binaire du keypad dans **Ghidra**, puis utilisé CodeBrowser et le **Symbol Tree** pour retrouver la fonction `main`. Le code décompilé était très condensé, mais j'ai pu suivre la logique générale.

- J'ai repéré un appel à `strcmp` utilisé pour comparer l'entrée, ainsi qu'une variable locale nommée `local68`.
- En suivant cette variable, j'ai retrouvé la fonction `decode_code`.
- La logique utilisait un tableau de valeurs encodées et une boucle appliquant un XOR avec une clé fixe, `0x5a`.
- J'ai écrit un script Python pour reproduire l'opération et retrouver le flag de l'exercice.

### Ce que j'en retiens sur XOR

XOR avec une clé fixe est une transformation réversible : `(valeur XOR clé) XOR clé = valeur`. Dans ce cas, ce mécanisme masque les données mais ne fournit pas une protection cryptographique robuste. Le fait que la logique et la clé soient intégrées au binaire permet de les retrouver par analyse.

Un secret embarqué dans une application distribuée peut ainsi être récupéré hors ligne. Dans un vrai système, cela peut contribuer à contourner une vérification ou exposer une clé, un jeton ou un mot de passe. Il faut distinguer encodage/obfuscation et chiffrement robuste ; même un bon algorithme ne protège pas une clé secrète si elle est facilement récupérable dans le client.

## Reverse engineering et applications web

J'ai clarifié qu'une analyse statique ne nécessite pas obligatoirement un binaire compilé : elle peut aussi porter sur du code source. Le reverse engineering d'un exécutable compilé est toutefois un cas classique, où l'on remonte des instructions machine vers une représentation approximative de la logique.

Pour les sites web, le navigateur reçoit le frontend (HTML, CSS, JavaScript et ressources), qui peut être inspecté avec les DevTools. Le code backend qui tourne sur le serveur n'est normalement pas envoyé au visiteur ; observer les requêtes et réponses ne donne pas automatiquement accès au code source serveur.

## Analyse dynamique : GDB

J'ai commencé à déboguer le binaire avec GDB. L'idée est de placer un breakpoint avant la comparaison de l'entrée, relancer le programme avec `run`, puis inspecter l'état au point d'arrêt. `info registers` affiche les registres ; sur Linux x86-64, `RIP` indique l'adresse de l'instruction en cours, tandis que `RDI` et `RSI` servent généralement aux deux premiers arguments d'une fonction. Avec `x/s $rdi` ou `x/s $rsi`, on peut examiner les chaînes pointées par ces registres, par exemple juste avant un appel à `strcmp`.

Cette partie est plus difficile à suivre : il faut relier les adresses mémoire, les registres et les instructions au déroulement du programme.

## Exécution symbolique : première introduction

J'ai ensuite commencé l'exécution symbolique, en étudiant la fonction `validate` et un script Python qui retrouve le flag. Contrairement à la recherche d'une chaîne en clair ou au décodage de données intégrées au binaire, l'exécution symbolique représente certaines entrées par des variables inconnues et transforme les conditions du programme en contraintes. Un solveur SMT, tel que Z3 utilisé par le framework Python `angr`, cherche des valeurs satisfaisant ces contraintes.

La room présente rapidement la technique ; je la considère comme une introduction, pas comme une compétence déjà maîtrisée. L'exécution symbolique peut être coûteuse : le nombre de chemins augmente vite, et une solution du solveur satisfait les contraintes sans être nécessairement l'unique réponse attendue.
